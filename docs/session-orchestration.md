# Метод работы: главная сессия + тематические сессии

Как вести проект в Claude Code (desktop) одной **главной сессией**, которая раздаёт задачи короткоживущим
**тематическим сессиям**, сводит их работу и держит git. Файл не привязан к проекту: скопируйте его в новый
репозиторий и скажите главной сессии: «работаем по `docs/session-orchestration.md`».

## 1. Роли

| Кто                                                             | Что делает                                                                                                                      | Чего не делает                                                                     |
| --------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| **Пользователь**                                                | ставит цели, принимает решения, смотрит результат глазами, запускает тяжёлые прогоны                                            | не пишет брифы и не следит за сессиями                                             |
| **Главная сессия** (одна, живёт долго, периодически `/compact`) | обсуждает и решает, ведёт общий контракт и общие файлы, пишет брифы, запускает и архивирует сессии, проверяет, коммитит и пушит | не делает объёмную работу внутри модулей (мелкие правки по просьбе модуля — можно) |
| **Тематическая сессия** (одна задача, потом в архив)            | работает только в папках своего модуля, пишет тесты, обновляет отчёт модуля, отвечает 1–3 строками                              | не трогает чужие папки и общий контракт, не делает git, не ставит зависимости      |

## 2. Подготовка проекта (один раз)

1. **`CLAUDE.md`** — ключевые решения («не пересматривать без главной сессии»), команды, стек, архитектура
   в одной картинке, таблица модулей и правила для сессий (раздел 6 ниже — скопировать почти дословно).
2. **Общий контракт** — папка с типами, которыми обмениваются модули (у нас `src/shared/`). Ей владеет только
   главная сессия. Каждый модуль экспортирует публичный API из `src/<модуль>/index.ts`, другие импортируют только оттуда.
3. **Уставы модулей** — `docs/sessions/<модуль>.md`: зона ответственности, папки, API, ограничения, порт dev-сервера.
4. **Отчёты модулей** — `docs/reports/<модуль>.md`, ≤40 строк: API · готово · проблемы и ловушки · что осталось.
   Это и есть долговременная память модуля: новая сессия читает отчёт, а не историю старой сессии.
5. **`docs/STATUS.md`** — состояние проекта: решения, вехи, план волн, что не проверено. Ведёт главная сессия.
6. **Изоляция параллельной работы в одной папке:** у каждого модуля свой порт dev-сервера, свои dev-страницы
   (`dev/<модуль>.html`), свои e2e-спеки (`e2e/<модуль>/`). Тестовые медиа и секреты — в `.gitignore`.
7. **Память главной сессии** (auto-memory) — только то, чего нет в репозитории: предпочтения пользователя,
   внешние ссылки, договорённости о протоколе.

## 3. Цикл одной задачи

1. **Пользователь** формулирует желание («текст должен появляться, а не подсвечиваться»).
2. **Главная сессия** разбирает его по модулям; если нужно, **сначала меняет общий контракт** (новые поля
   необязательные, версия в комментарии), записывает план в `STATUS.md`.
3. Запускает сессии **волнами**: в одной волне — независимые задачи в разных папках, **не больше 2–3 одновременно**.
   Следующая волна — то, что зависит от результатов предыдущей (обычно фронт подключает то, что сделали модули).
4. Тематическая сессия делает задачу, гоняет проверки **своей папки**, обновляет свой отчёт, отвечает 1–3 строками.
   Нужна правка в чужом модуле — **описывает её точно** (файл, тип, поле, где заполнять) в отчёте.
5. Главная сессия: читает отчёты точечно (grep по «Что осталось», «для главной», «фронту»), вносит мелкие
   межмодульные правки сама, прогоняет **полный** typecheck / тесты / lint / build, коммитит, пушит, архивирует сессии.
6. Пользователю — короткий итог: что поменялось, что проверено, **что не проверено глазами**, что посмотреть.

Если волна оставляет проект в нерабочем состоянии (контракт расширен, а UI ещё не догнал) — коммит локально,
**пуш после следующей волны**, чтобы не ломать деплой.

## 4. Экономия токенов

- **Сессия = одна задача.** Свежая сессия (`context: fresh`) с коротким брифом; после отчёта — в архив.
  Исключение: следующую задачу того же модуля, пока сессия ещё «тёплая», можно отправить ей же сообщением.
- **Название** — `<Проект>: <модуль> — <задача> · <модель>`, чтобы в списке было видно модель.
- **Модель по задаче:** Opus — архитектура, рендер, сложная графика/эффекты; Sonnet — фронт, интеграции, логика;
  Haiku — механика (переименования, документация, простые тесты).
- **Читать точечно:** grep и нужные строки, а не файлы целиком; не исследовать чужие модули.
- **Проверки по месту:** сессия — свои тесты и lint; полный прогон — главная при сведении. В браузере —
  скриптовые проверки с текстовым выводом, скриншоты только когда без них никак. Оценку «красиво ли» делает пользователь.
- **Тяжёлые прогоны** (замеры моделей, длинный рендер, полные e2e) — готовой командой, запускает пользователь,
  по одному на машину.
- **Главная сессия** — `/compact`, когда история разрослась; всё важное к этому моменту уже лежит в файлах.

## 5. Шаблон брифа

```
Ты — сессия «<модуль>» проекта <Проект>. Прочитай `CLAUDE.md`, `docs/sessions/<модуль>.md`,
`docs/reports/<модуль>.md`; из `<другой отчёт>` — только раздел API.

Запрос пользователя: <одной-двумя фразами, своими словами>.
Задачи (только `<папки модуля>`):
1. <что сделать, с ограничениями и критериями>
2. …
Если не хватает чужого API — не правь чужое, опиши точную правку в отчёте.
Параллельно работает <кто, где> — не трогай. Порт <N>. Без git и установки зависимостей.

Готово, когда: typecheck без ошибок в своих папках, `<тесты своей папки>`, `<lint своей папки>` зелёные,
есть тесты на <ключевое>. Обнови `docs/reports/<модуль>.md` (≤40 строк) и ответь 1–3 строками.
```

`background` (для свежей сессии): 2–4 предложения — что за проект, где мы сейчас, зачем эта задача, кто ещё работает.

## 6. Правила для тематических сессий (в `CLAUDE.md`)

1. Работай только в своих папках. Правка чужой области или контракта — опиши и передай главной сессии.
2. Не делай git commit/push и не создавай ветки — это делает только главная сессия.
3. Не ставь зависимости и не правь `package.json`/lock-файл (параллельные установки ломают lock) — попроси главную.
4. Ключевые решения не пересматривай сам — предлагай главной сессии.
5. В конце — обнови `docs/reports/<модуль>.md` и ответь главной 1–3 строками.
6. Ничего не начинай без задачи.
7. Свои dev-страницы и свой порт dev-сервера; общий вход приложения не трогай.
8. В автотестах — синтетические данные; реальные медиа и чужие тексты в репозиторий не копировать.
9. Тяжёлые этапы — по очереди, по одной модели/процессу за раз; тяжёлые прогоны — только после «машина свободна».

## 7. Чек-лист сведения (главная сессия)

- [ ] `git status` — изменения только в ожидаемых папках.
- [ ] Отчёты: запросы к другим модулям выполнены или поставлены в план.
- [ ] Полный typecheck, все тесты, lint, prod-сборка — зелёные (или осознанно локальный коммит без пуша).
- [ ] Коммит с понятным сообщением по модулям, пуш.
- [ ] `STATUS.md` обновлён (веха, что не проверено), сессии заархивированы.
- [ ] Пользователю: итог, что не проверено, что посмотреть.

## 8. Безопасность и git

- Секреты — только в `.env` (gitignored); в репозитории — `.env.example` с пустыми значениями.
- Коммиты от noreply-адреса хостинга кода.
- Перед публикацией репозитория: поиск токенов по **всей истории** (`git log --all -p | grep` по шаблонам ключей),
  список всех когда-либо добавленных файлов, локальные пути и e-mail, медиа и веса моделей, `npm audit`, лицензия.
- Действия наружу (пуш, смена видимости репозитория, публикация) — по явной просьбе пользователя.
